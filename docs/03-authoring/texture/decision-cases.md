# Texture & UV Decision Cases — K3 Pilot

**Status:** FOUR `SOURCE-GROUNDED_CANDIDATE` cases; case facts pinned, decisions and positive/negative/ambiguous examples **hypothetical**, selection fixture AUTHORED BUT NOT EXECUTED; not a trained AI system, Texture/UV authoring PASS, user approval, or native Blockbench evidence. 2026-10-29.

**Owners:** [Texture & UV Standard](standard.md) is normative; [K2 coverage](knowledge-coverage.md) diagnoses gaps; [K1 research](research-sources.md) gives broad links/limitations; this file contains **only** the four discriminating choices. Geometry shape/rig is frozen. Modelling owns UV Layout/lock/PASS; Texturing owns atlas/styling/material/PBR and Texture Verify. The shared AUTHORING runtime does not collapse ownership.

**Source requirements:** Use only current approved view/claim evidence, exact Cube/face/texture UUID, signed UV and current atlas bytes for a dependent decision. The pinned source files below establish **external and internal observed facts**, not the appearance of a user's asset. Source SHA-256 is computed from the exact UTF-8 file text fetched at the specified Git ref; Git blob object IDs are a distinct SHA-1 identifier. `format_version` is file schema metadata, not an attestation that a particular installed Bedrock/Blockbench build is compatible. Rolling official docs remain explanatory only, without a source-content/version attestation.

**Selection discipline:** One case is suggested from an exact semantic question, never from its common parent heading. Ties, unknown target/version, untrusted source/revision, insufficient live face/reference evidence, or a mismatch between current state and the case -> `REVIEW_REQUIRED`/abstain. A selection result never directly invokes `manage_uv_layout`, Painter, `manage_render_profile`, or any other mutation. `manage_uv_layout` is still **UNREGISTERED**.

## UV-P01 Mirrored Texel Reuse Asymmetric Identity

- **Decision:** whether two actual UV islands/faces may share identical bitmap texels, rather than simply matching footprint, physical span or mirrored geometry. The artwork and orientation must be compatible.
- **Source fact (inspected):** S01 Enderman has separate left/right arm and leg bones, repeated Cube `uv: [56, 0]` and authored `mirror: true` on left bones. S05 `discoverUvStackProposals` publishes a matching-footprint **REVIEW** candidate but a structurally compatible explicit stack group can be `READY`. Neither fact establishes identical user-approved artwork or accepts a stack on another model.
- **Positive case (hypothetical):** the current approved reference explicitly shows the **same unmarked, symmetric pattern** on two exact identified Cube faces, their texture UUID, orientation and physical pixel extents are known, and no face-specific wear/contact/exposure/decals conflict. Recommend **eligible intentional shared UV review**; continue only through the existing Modelling-owned constraint/stack workflow.
- **Reject case (hypothetical):** one mirrored sleeve/eye panel carries a unique symbol, letter, dirt patch or oriented stripe while the other does not. Recommend **UNIQUE UV ownership** (or preserve existing independent regions); never stack solely because geometry matches. Protect mirrored mark alignment and existing painted pixels.
- **Ambiguous case (hypothetical):** only the front reference exists, the opposite mark is unseen, source mirror intent is uncertain, or a texture revision has changed. Return **REVIEW_REQUIRED**, no new stacking constraint.
- **Required evidence:** approved reference view and claim ID for **both** surfaces; Cube UUID + face direction; current texture UUID, source fingerprint, signed corner/rotation, pixel scale; explicit mark/identity, exposure/contact/UV-reuse intent. If any is unavailable, remain advisory.
- **Owner / consumer:** `mcp/lib/uv/stacking.ts`, `mcp/lib/uv/semanticPlanner.ts` (Modelling UV selection); `mcp/lib/texture/geometrySignalCompiler.ts` and `mcp/lib/texture/treatmentPlan.ts` inspect conflicting downstream paint ownership. Existing `mcp/tests/uv-stacking-proposals.test.ts` is the regression owner; the K3 fixture verifies source-case retrieval separately.
- **Test and proof:** a same-footprint pair with a unique mark must not become auto-stacked; unknown view must abstain; a verified symmetric pair still needs an explicit artist/source choice. Native proof requires actual UV atlas, face-local image orientation and marked-model front/side views against the same reference, plus untouched shared pixels after save/export.
- **Source IDs / risk:** S01, S05, S06; additional official Bedrock schema B02 and Unreal lightmap comparison E01 from [K1](research-sources.md) are advisory, not blanket constraints. Risk: identity loss, reversed text, shared-pixel overwrite, painted atlas corruption.
- **Status:** source facts inspected, decisions hypothetical; **NOT RUN / NOT NATIVE-VERIFIED**.

## TEX-P01 Reference Material Palette Pixel Clusters

- **Decision:** select a material-specific `surface_pattern` and base/shadow/highlight/identity palette **from the currently approved texture reference**, on an exact mapped region at sufficient physical texel resolution. Never substitute object-name guesses for actual colors or material direction.
- **Source fact (inspected):** S07 `generateTexturePalette` generates an HSL shade ladder **given an explicit base**, not a source-image interpretation. S08 lists 17 qualitative recipes (including `wood_grain`, `painted_wood`, `painted_metal`, `stone_cluster` and `cloth_weave`). S06 `planTextureTreatment` resolves a **caller-supplied** pattern, evidence state, region/face targets and render profile, while leaving unknown references unresolved. None of these reads the user reference or demonstrates successful pixel artwork.
- **Positive case (hypothetical):** approved front/side reference shows a painted wooden panel with confirmed paint base color, sparse visible underlying grain, distinct identity accent, a known grain direction and adequate face-local pixel density. Suggest conditional `painted_wood` treatment, a compact role palette and existing staged painting order (base -> value/form -> material -> identity -> detail), **not an automatic bitmap**.
- **Reject case (hypothetical):** the reference actually shows clean painted metal, with hard edge highlights and no grain. Reject `painted_wood` and random grain/noise even though both objects might be described as 'wooden/metallic props' in words. The true target material and palette outrank a recipe keyword.
- **Ambiguous case (hypothetical):** photograph is blurred/overexposed, the surface is unseen, local UV density is too low for claimed weave detail, or a source region cannot be bound to actual faces. Return **REVIEW_REQUIRED**, preserve unknown colors and do not create microtexture.
- **Required evidence:** actual approved image pixels/source claim, exact material/face cohort IDs, UV/bitmap scale, color roles with origin, region directionality and current atlas revision; render_profile and optional PBR intent must be supplied separately, never inferred from a pattern name.
- **Owner / consumer:** existing `mcp/lib/texture/treatmentPlan.ts`, `mcp/lib/texture/surfacePattern.ts` and `mcp/lib/texture/palette.ts`, consumed by Texturing specialist before `paint_texture_transaction` or native brush. No new shader, procedural noise default or mandatory PBR. `mcp/tests/texture-treatment-intelligence.test.ts` and `texture-palette.test.ts` retain technical coverage.
- **Test and proof:** the same generic category word with two dissimilar approved references must not select the same paint instruction; missing color/view must abstain; final verdict requires material identity, cluster readability, palette preservation and matched mapped-model views, not number of colors or low isolated-pixel ratio.
- **Source IDs / risk:** S06, S07, S08, S11; the [Blockbench Minecraft Style Guide](https://blockbench.net/wiki/guides/minecraft-style-guide/) (Texturing / Color Ramps & Palettes, Shading, Entity Textures) was reviewed on 2026-10-29 as **rolling official guidance without pinned immutable bytes or target compatibility**. Rights: linked educational guidance only, no copied artwork. Risk: generic noisy textures, palette drift, reference identity loss, view inconsistency.
- **Status:** source facts inspected, artistic efficacy untested; **NOT RUN / NOT VISUAL-VERIFIED**.

## TEX-P02 Cross Cube Seam Observed Continuity

- **Decision:** distinguish a genuine, intended continuous **3D adjacent-face seam** from an intentional material boundary, accidental atlas bleed or insufficiently sampled evidence.
- **Source fact (inspected):** S09 implements bounded intra-Cube scan and a separate pure cross-Cube edge comparison, with nontransitive/ambiguous edge groups, material/alpha scope, omission counts and `not_evaluated` visual status. S06 requires an explicit reference edge observation for `REQUIRED` continuity and labels any caller handoff `CALLER_DECLARATION_UNVERIFIED`. Neither is an installed all-face scanner or visual seam PASS.
- **Positive case (hypothetical):** a verified reference shows one continuous stripe across two distinct Cube faces; exact world-space endpoints, orientation, material, texture ownership, comparable physical pixel samples, source observation and current atlas revision are all supplied. Suggest **bounded cross-Cube seam diagnostic**, not an automatic pixel correction or whole-model clean verdict.
- **Reject case (hypothetical):** two touching parts intentionally have different colors/materials or a hard structural border. Select `INTENTIONAL_BOUNDARY`; do not treat contrast as a seam defect. Likewise, 2D padding that merely dilates an island cannot by itself prove the opposing 3D edge matches.
- **Ambiguous case (hypothetical):** two edges are near but not coincident, sample counts differ, one face is missing/disabled, reference observation is absent, alpha semantics unknown or a T-junction/multiple edge group exists. Return **NOT_EVALUATED / REVIEW_REQUIRED**, never `CLEAN`.
- **Required evidence:** actual paired Cube UUID + face + edge and parent/world transforms, reference observation ID/revision for same exact pair, expected continuity/material intent, current image/UV/texture UUID+digest, comparable physical samples and known alpha interpretation.
- **Owner / consumer:** `mcp/lib/texture/seamContinuity.ts`, `mcp/lib/texture/treatmentPlan.ts` and existing Validation/Texture Verify route; `mcp/tests/texture-seam-continuity.test.ts` and `texture-treatment-intelligence.test.ts` already cover pure guards. K3 is advisory only; no new seam engine.
- **Test and proof:** correct paired stripes must produce a scoped candidate without claiming model-wide PASS; deliberate boundary must not be marked defect; unpaired/incomplete scope must remain unresolved. Native inspection requires fresh matched atlas and model view around the actual seam, with same renderer and saved source identity.
- **Source IDs / risk:** S06, S09. [Adobe Substance 3D Painter Texture Set Settings](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/interface/texture-set/texture-set-settings) contrasts 2D vs 3D neighbor padding, but is **rolling, editor-specific guidance**, not a Bedrock acceptance rule; confirmed 2026-10-29. Risk: false seam-clean status, false-positive discontinuity, repainted intentional boundaries.
- **Status:** pure source mechanisms inspected, live edges unavailable; **NOT RUN / NATIVE SEAM PASS NOT EVALUATED**.

## TEX-P03 Emissive Eyes Material PBR Render

- **Decision:** distinguish a visually bright eye/panel from an explicitly bound Minecraft render material and from an optional MER/MERS Texture Set. The three are different decisions; no file name or bright RGB value alone authorizes emissive claims.
- **Source fact (inspected):** S02 pinned Creaking `client_entity` binds `materials.default=creaking` and `materials.eyes=creaking_eyes`, and separate default/eyes textures and render controllers. S03 controller `controller.render.creaking_eyes` selects a material array conditionally, uses `Texture.eyes`, sets `ignore_lighting: true`, and gates head visibility by `variable.has_emissive_eyes`. S02 separately defines this variable in a script. S04 eye texture set uses color `creaking_eyes` and `metalness_emissive_roughness_subsurface=creaking_eyes_mers` with `format_version=1.21.30`. This **complete linkage** is far stronger than the asset name alone, yet remains source inspection, not measured gameplay rendering.
- **Positive case (hypothetical):** the actual target reference visibly needs illuminated eyes and the user specifies the target renderer/material behavior. The asset has confirmed intended material assignment and explicit color+render/PBR roles. Suggest separated `surface_pattern`, `render_profile` and optional `pbr_texture_set` *for review*, with Bedrock target compatibility checked before authoring.
- **Reject case (hypothetical):** a texture named `glow_eyes` has bright cyan RGB and an optional MERS file but has no confirmed renderer or material binding. Reject an automatic `emissive_mask`/`entity_emissive` claim; MERS green is not automatically an entity emissive render material.
- **Ambiguous case (hypothetical):** renderer or image format requirement, material code, alpha meaning, Creaking-style conditional state, or current render-binding evidence is unknown. Return **REVIEW_REQUIRED / unverified_custom**, preserving user reference rather than guessing runtime behavior.
- **Required evidence:** current approved visual identity and user target, native texture UUID/bitmap alpha, exact known material code or explicit custom contract, bound role and format (including TGA/PNG requirements), PBR channel/TextureGroup selection, and target renderer build/visual outcome. External Creaking render-controller wiring is **reference evidence only**; LazyDesigner does not author the Resource Pack graph or gameplay state.
- **Owner / consumer:** `mcp/lib/texture/renderProfile.ts`, `mcp/lib/texture/alphaSemantics.ts`, `mcp/lib/texture/pbrContent.ts` and Texturing treatment plan. Native PBR serialization is represented by S10 Blockbench source. Technical test owners: `mcp/tests/texture-treatment-intelligence.test.ts` and `pbr-channel-contract.test.ts`.
- **Test and proof:** with a complete known binding, propose a scoped render/PBR review; when only a bright pixel/name or MER is known, abstain; mismatched render profile and alpha/PBR must not silently become READY. Actual installed Blockbench preview and target Minecraft renderer remain separately unverified.
- **Source IDs / risk:** S02, S03, S04, S10, S11; Mojang file-format versions are **not** proof of current native runtime compatibility. Risk: false glow, incorrectly interpreted alpha, double/unsupported emissive setting, invalid export.
- **Status:** pinned source binding observed, target gameplay/runtime behavior **NOT EXECUTED**.

## Positive / Negative / Ambiguous Selection Fixture — K3 Only

These are **scenario specifications for a future consumer**, not source-observed asset outputs. A title-match in the existing index may suggest a case, but cannot classify or authorize a paint/UV operation based only on a keyword.

| ID | Query cue for unique case retrieval | Positive preconditions | Negative stop / different decision | Ambiguous abstention |
| --- | --- | --- | --- | --- |
| UV-P01 | `mirrored texel reuse asymmetric identity` | Exact same observed art + compatible UV owners | Logo / identity asymmetry -> UNIQUE | Unseen opposite side or stale atlas -> REVIEW_REQUIRED |
| TEX-P01 | `reference material palette pixel clusters` | Approved material, value colors, face and texel scale | Clean metal does not receive wood grain | Missing source colors, low density -> REVIEW_REQUIRED |
| TEX-P02 | `cross cube seam observed continuity` | Explicit 3D edge pair + reference + comparable samples | Intentional distinct material boundary -> exclude | Missing samples/edge orientation -> NOT_EVALUATED |
| TEX-P03 | `emissive eyes material pbr render` | Actual material binding + render target and PBR roles | Glowing texture name/RGB alone -> no emissive | Unknown binding/alpha/renderer -> REVIEW_REQUIRED |

**Expected selector behavior:** `mirrored texel reuse` selects only `UV-P01`; `reference material palette` only `TEX-P01`; `cross cube seam` only `TEX-P02`; `emissive eyes` only `TEX-P03`. A generic request like `material` can match multiple case titles and MUST abstain from case-specific guidance. An unrelated `animation rig pivot` query selects none. A case body edit must change its section SHA-256 without silently changing other cases; Runtime will need a **separate K4 design/consumer** before any source-grounded case selection becomes an authoring feature.
