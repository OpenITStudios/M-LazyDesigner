# LazyDesigner Animation Reference Contract

Updated: 2026-09-18

This document owns the canonical content of packaged `ANIMATION.md` files generated by ChatGPT Reference Preparation for Codex.

It does not own Runtime animation implementation, final bone coordinates, keyframe authoring mechanics, controller setup, or playback verification. Those remain downstream responsibilities of LazyDesigner Animation + Codex + Runtime/Blockbench.

## Objective

`ANIMATION.md` should explain only the motion information that materially helps Codex author the intended animation correctly.

It must answer:

```text
what animation is needed
what parts participate
what drives the motion
what contacts / attachments must remain valid
what key poses define the action
how timing is organized relatively
what articulation / deformation risks matter
what secondary motion matters
which approved images own motion intent
what remains unknown or blocking
```

It must not become a frame-by-frame implementation recipe unless the user explicitly requires that level of precision.

## Authority Order

```text
1. explicit current user requirement
2. approved animation / pose visual reference
3. REFERENCE.json structured facts
4. ANIMATION.md motion projection
5. downstream Codex interpretation
```

If a required pose cannot be achieved because Geometry/rig structure is unsuitable, that is a Geometry blocker. Do not compensate for structural defects with arbitrary animation keys.

## Conditional Voxel 3D Style-Lock Projection

An established [Voxel 3D Style Bible](../pixel-art/style-lock.md#stylized-minecraft-voxel-3d--conditional-artist-style-bible) may contribute source-supported motion personality (for example heavy settling versus quick recovery) to existing Key Poses, Relative Timing or Motion Constraints when it changes the requested clip. It does not supply a default FPS, keyframe count, amplitude, contact window, controller, hierarchy or approval. Preserve missing/contradictory evidence as unknown; native playback remains unverified until actually observed. Do not add a new handoff field or preload the whole Style Lock.

## Canonical File Name

```text
ANIMATION.md
```

Create this file only when:

```text
animation_required = true
```

and motion guidance materially helps downstream authoring.

A trivial known mechanical loop may not need a dedicated document when the requirement is already fully explicit and no ambiguity exists.

## 1. Animation Target

State the requested motion in one concise sentence.

Example:

```text
Create a one-shot harvesting motion where the farmer swings the supplied tool into the cinnamon target and returns toward the ready stance.
```

Do not include implementation mechanics here.

## 2. Motion Type

Record the high-level motion class only when useful.

Recommended values:

```text
LOOP
ONE_SHOT
STATEFUL
REACTIVE
IDLE
LOCOMOTION
MECHANICAL_CYCLE
SECONDARY_MOTION
CUSTOM
```

This is descriptive guidance, not a controller prescription.

If a more specific type is user-defined, preserve that wording instead of forcing it into a generic class.

## 3. Participating Parts

List only semantic parts that materially participate in the motion.

Example:

```text
- torso — primary body driver
- right_upper_arm — main swing driver
- right_lower_arm — follows swing and controls tool arc
- right_hand — maintains tool attachment
- tool — rigidly follows right hand
- left_arm — balancing/counter-motion
- pelvis — limited weight shift
- legs — maintain stance and ground contact
```

Rules:
- use stable semantic IDs when they exist in `REFERENCE.json`;
- do not list every bone if it does not materially affect the animation;
- do not invent motion participation merely because a part could move;
- distinguish driver vs follower when it improves clarity.

## 4. Motion Relationship

Describe the causal motion structure, not exact rotations.

Useful relationships may include:

```text
primary driver
counter-motion
followers
phase relationship
chain propagation
delayed secondary motion
shared transform
bounded hinge/rotation
translation path
```

Example:

```text
right_upper_arm drives the harvesting swing
→ right_lower_arm follows to preserve tool arc
→ torso contributes limited rotation toward target
→ left arm provides counter-balance
```

For mechanical motion:

```text
main_shaft drives rotor rotation
→ linked_arm follows the visible linkage relationship
```

Do not create hidden kinematic assumptions not supported by reference or explicit requirement.

## 5. Key Poses

Key poses define visible motion intent.

Use the minimum set needed to make the action unambiguous.

Example:

```text
1. READY
   stable stance; tool prepared

2. ANTICIPATION
   tool moves away from target; body prepares force

3. SWING
   primary arm and torso move toward target

4. CONTACT
   tool reaches intended target while support contact remains stable

5. FOLLOW_THROUGH
   motion continues beyond contact without losing attachment

6. RECOVERY
   body returns toward ready/neutral state
```

Rules:
- key poses describe silhouette, direction, contact and intent;
- do not prescribe exact Euler values;
- do not require a universal number of poses;
- locomotion, loops, idles and mechanical cycles may use different pose structures;
- if approved keyframe/reference images exist, refer to their image IDs.

## 6. Relative Timing

Use relative timing when it materially helps action readability.

Preferred forms:

```text
percentage
normalized phase
relative duration words
```

Example:

```text
READY          ~0%
ANTICIPATION   ~20%
SWING          ~45%
CONTACT        ~55%
FOLLOW_THROUGH ~75%
RECOVERY       ~100%
```

These values express motion rhythm, not final frame numbers.

Do not invent exact FPS, frame counts or durations unless explicitly required or supported by approved reference.

For cyclic motion, timing may instead describe:

```text
phase offset
contact/release phase
loop seam
repeated cycle relationship
```

## 7. Contact / Attachment Invariants

Record what must remain planted, connected, touching or intentionally separated during the motion.

Examples:

```text
feet remain planted during the harvesting swing
right hand maintains tool attachment
jaw remains connected to cheek/head coverage through open/close
wheel remains centered on axle while rotating
slider maintains overlap with its guide throughout travel
wing root remains attached to torso through fold
```

These are correctness constraints, not keyframe coordinates.

If a required invariant cannot be maintained because Geometry is wrong, mark the animation stage blocked and return the issue upstream.

When an attachment/effect point is represented by a Locator, describe the semantic parent Group/Bone that drives it. Current authoring animates the parent Group/Bone; the Locator follows that transform. Do not prescribe direct Locator keyframes.

## 8. Joint / Deformation Constraints

Include only motion-relevant joint risks.

Examples:

```text
shoulder must remain visually closed through swing
hip must not expose a large crotch gap
knee overlap must survive expected stance bend
jaw opening must not expose unintended side gaps
wing fold must clear torso without detaching root
mechanical hinge must rotate about the supported axis
supported joint/hinge rotation limits must not be exceeded when explicitly evidenced
```

Do not copy the entire rig-deformation profile into this document.

Only include constraints that affect the requested animation.

## 9. Secondary Motion

Document only when material to the result.

Examples:

```text
scarf follows torso motion with slight delay
long tail follows body turn as a delayed chain
backpack remains mostly rigid with subtle body-following motion
plant leaves use mild delayed sway after stem movement
```

Do not add secondary motion merely to make the animation look more complex.

For identity-critical action, primary motion correctness always outranks secondary polish.

## 10. Motion Constraints

Include explicit motion requirements that do not belong cleanly elsewhere.

Examples:

```text
- supplied tool must remain in right hand for the full clip
- feet should not slide before recovery
- rotor speed should read as continuous rather than stop-start
- motion should return cleanly to the starting pose for loop continuity
```

Avoid generic animation advice such as "use good easing" unless the user explicitly requested a particular motion quality and the wording materially clarifies the target.

## 11. Visual References

Refer to packaged image IDs, not only filenames.

Example:

```text
Primary motion authority:
- IMG_ANIM_01 — key pose / keyframe guide

Supporting articulation authority:
- IMG_RIG_01 — shoulder/hip/knee overlap reference

Supporting action context:
- IMG_POSE_01 — harvesting contact pose
```

Each image ID must exist in `REFERENCE.json`.

Do not describe visual facts that are already obvious from the image unless the relationship is easy to misread or technically important.

## 12. Unknowns / Blockers

List only animation-relevant uncertainty.

Example:

```text
Blocking:
- exact tool contact target is not yet confirmed

Non-blocking:
- minor head follow-through intensity is unspecified
```

Rules:
- do not copy unrelated Texture or Geometry unknowns;
- a Geometry/rig blocker affecting motion should be identified explicitly as upstream-owned;
- if no animation blocker exists, say only that the animation stage has no blocking unknowns when useful.

## Character / Creature Guidance

For articulated organic subjects, prioritize when relevant:

```text
action silhouette
weight direction
support/contact
joint bend direction
preferred motion axis / supported rotation envelope when evidenced
twist policy when constrained by the rig/reference
joint closure/overlap
head/torso counter-motion
limb sequencing
follow-through
secondary appendage motion
```

Do not force humanoid conventions onto non-humanoid creatures.

## Mechanical Guidance

For mechanical motion, prioritize when relevant:

```text
driver assembly
axis / travel direction
linked follower relationship
clearance
contact / overlap invariant
cycle / return state
```

Do not invent internal mechanisms absent from the approved reference.

## Plant / Foliage Guidance

For plant motion, distinguish:

```text
rigid sway
segmented bend
secondary leaf motion
texture-only motion
nonparticipating regions
```

Use the minimum meaningful motion hierarchy. Do not prescribe one bone per leaf by default.

## Relation to `REFERENCE.json`

`REFERENCE.json` owns structured facts such as:

```text
animation_required
semantic part IDs
articulation relationships
animation guidance identity
image IDs
readiness
blocking/non-blocking unknowns
```

`ANIMATION.md` turns only the relevant subset into a concise motion brief.

Do not create a second independent set of facts that can drift from `REFERENCE.json`.

## Relation to `GEOMETRY.md`

`GEOMETRY.md` owns structure, proportions, attachments, representation and rig-readiness from the modelling perspective.

`ANIMATION.md` may reference only the motion-relevant consequences, for example:

```text
GEOMETRY.md:
upper leg overlaps pelvis for articulation

ANIMATION.md:
hip overlap must remain visually closed during the harvesting stance shift
```

Do not duplicate the entire Geometry document.

## Relation to `TEXTURE.md`

Texture does not normally affect motion planning.

Only mention texture/material information in `ANIMATION.md` when it materially affects motion readability or effect ownership, such as:

```text
emissive pulse timed to an animation event
alpha membrane whose fold silhouette matters
```

Keep ordinary material/palette instructions out of `ANIMATION.md`.

## What Must Not Appear

Do not put these in `ANIMATION.md` unless explicitly required by the task:

```text
exact final Euler rotations
exact Blockbench pivot coordinates
full frame-by-frame key list
universal FPS
arbitrary keyframe density
MCP Tool schemas
Tool-call sequences
controller implementation recipes
gameplay/BP integration instructions
full Geometry hierarchy dump
full Texture/material brief
generic animation tutorials
invented motion not supported by user/reference
```

## Compact Example

```markdown
# Animation Reference

## Animation Target
Create a one-shot harvesting swing using the supplied tool against the cinnamon target.

## Motion Type
ONE_SHOT

## Participating Parts
- torso — limited primary body rotation
- right_upper_arm — main swing driver
- right_lower_arm — follows swing and maintains tool arc
- right_hand — keeps tool attached
- tool — rigidly follows hand
- left_arm — counter-motion
- pelvis / legs — limited weight shift while maintaining stance

## Key Poses
1. READY — stable stance, tool prepared
2. ANTICIPATION — tool moves back, torso prepares motion
3. SWING — arm and torso move toward target
4. CONTACT — tool reaches target, feet remain planted
5. FOLLOW_THROUGH — motion continues past impact
6. RECOVERY — returns toward ready stance

## Relative Timing
READY ~0%
ANTICIPATION ~20%
SWING ~45%
CONTACT ~55%
FOLLOW_THROUGH ~75%
RECOVERY ~100%

## Contact / Attachment Invariants
- right hand maintains tool attachment throughout
- feet remain planted until recovery
- tool contact occurs at the intended cinnamon target

## Joint / Deformation Constraints
- shoulder remains visually closed during the swing
- hip does not expose a large gap during weight shift
- knees maintain overlap during stance adjustment

## Visual References
- IMG_ANIM_01 — primary keyframe guide
- IMG_POSE_01 — contact/action pose
- IMG_RIG_01 — joint overlap guidance

## Unknowns / Blockers
No animation-stage blocking unknowns.
```

## Completion Condition

`ANIMATION.md` is ready when:
- the intended motion is unambiguous;
- participating semantic parts are identified without unnecessary hierarchy dumping;
- key poses are sufficient to communicate the action;
- relative timing is included only where useful;
- required contact/attachment invariants are explicit;
- motion-relevant deformation risks are captured;
- relevant image IDs are linked;
- animation blockers are explicit;
- no unsupported implementation details are invented.
