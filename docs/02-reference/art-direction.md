# Cross-Domain Art Direction — Minecraft Voxel Assets

This document is the **single semantic owner for shared 3D visual-family direction** across Geometry, Texture and Animation. The source of asset-specific truth remains current user instructions, approved reference images, confirmed dimensions and accepted project conventions; this document does not approve any style or asset automatically.

**Ownership:** [Pixel Art Style Lock](pixel-art/style-lock.md) retains its specific pixel-art profile syntax and standalone-asset grammar. This document owns only **cross-domain 3D art direction**. [Reference Preparation Policy](policy.md) owns typed authority and [the existing Reference Package](package/schema.md) carries only current supported facts. The Geometry, Texture and Animation domain standards own implementation. No second Style Lock identity, state registry, engine or independent routing stage is introduced.

**Evidence status:** The generic voxel direction below is advisory and provisional until grounded against user-approved asset or representative collection. Do not infer exact palette, proportions, axes, timing, image-rights permission, or actual improvement from a Markdown example.

## Use during an active authoring decision

1. **Anchor in the asset:** Start from the *current* approved user reference, Reference Package, target Bedrock format and actual editor state—not a research title, preview or marketplace style.
2. **Ask one unresolved question:** Only when it changes the active stage's visual choice, select **one relevant VC row** below. If evidence is missing, incompatible or conflicting, keep `UNKNOWN` / `REVIEW_REQUIRED`; never fill gaps with a global preset.
3. **Hand off narrowly:** Control retains one active specialist. Geometry uses existing source/section-hashed G-P01–08 Recipe candidates; Texture reads on-demand UV-P01 / TEX-P01–03 resources; Animation uses its existing Standard. Pass only supported decision-changing facts through `GEOMETRY.md`, `TEXTURE.md` or `ANIMATION.md`.
4. **Evaluate separately:** A selected case, matching hash or technically valid model is not source-image fidelity, permission to paint/animate, user approval or visual PASS. Source checks and actual native/reference-matched review are different evidence.

This adds no per-Cube lookup, new Gateway tool, second Style Lock, parser, runtime routing layer or automatic mutation. [Full source classification](../04-system/authoring-knowledge-maturity.md#visual-craft-source-disposition-crosswalk--maintenance-only) is for maintainers, not ordinary asset context.


## Professional visual reasoning — original design versus faithful reconstruction

**Purpose:** give the existing Reference Preparation and active Geometry/Texture/Animation specialist a *decision-making method* for professional-looking voxel assets. It is conditional cross-domain art direction, not a style preset, new Skill, generated output schema, independent art critic service, or promise that a model is visually excellent. Apply it only at a genuine design ambiguity or review boundary, never per Cube/pixel.

**Choose the visual authority before proposing shape:**

- **FAITHFUL RECONSTRUCTION:** A supplied and approved reference controls visible identity, silhouette, proportions, material regions and intentional asymmetry. Explore alternative *construction methods*, not alternative character designs. Unknown rear geometry, hidden contacts or unseen material remain unresolved, not artistically improvised facts.
- **ORIGINAL DESIGN:** The user authorizes creation of a new concept from a brief or broad style direction. Propose a coherent artistic interpretation using reversible creative choices; keep those choices `PROVISIONAL` until visually reviewed and accepted. A marketplace example is inspiration for general craft (hierarchy, palette relationship, geometry economy), not a substitute source for distinctive motifs or permission to copy an asset. Once a target is approved, subsequent reconstruction follows that target.
- **HYBRID / RE-DESIGN:** Preserve explicitly locked attributes and identify exactly what the user permitted to change. Do not replace the source identity merely because a reference lacks a back view or a prompt says 'professional'.

**One compact art-direction hypothesis, only for a material choice:**

```text
Identity: what should read first at gameplay/thumbnail size?
Form: dominant mass rhythm, silhouette landmark, attachment, true negative space
Materials: primary / supporting / focal material roles, value separation, cluster scale
Motion (if required): weight, pivot, contact, anticipation/settle vocabulary
Evidence: which facts are seen, user-specified, provisional or unknown?
```

Reason from **large to small**: silhouette and proportion → recognisable secondary masses/negative spaces → value grouping and material contrast → identity marks → sparse micro-detail. The design is not automatically more professional because it contains more Cubes, higher texture resolution, glow, or more animation keyframes. When an original-concept decision has two genuinely different viable approaches, contrast at most 2–3 concise alternatives by the *specific criterion that changes* (for example strong squared guardian silhouette versus separated curved shoulder masses). Select one grounded option or request the missing artistic decision; never generate multiple full images or models by default. An already-approved reference bypasses this speculative choice.

**Art review under equivalent viewing conditions:**

1. **Form read:** inspect actual comparable front/side/three-quarter views (and back where identity depends on it), at normal intended display size; ask whether the subject, proportions, focal read, negative spaces and attachments survive when detail is suppressed. A hero render cannot hide a wrong rear silhouette.
2. **Value/material read:** for an approved source, compare mapped shaded model surfaces with the actual reference; look for readable primary/secondary/accent hierarchy, nonuniform material treatment, clean integer pixel clusters and deliberate quiet areas. Check important face orientation, unintended seams and markings that wrongly mirror. Flat-atlas aesthetics alone are insufficient.
3. **Motion read:** for animated assets, review the intended signature pose and contact/clearance at the critical time, not only a pleasing static frame. Material and geometry distinctions must survive the movement.
4. **Decision:** name the **highest identity-bearing mismatch**, its exact owning domain, and the smallest justified correction. Mark `PASS | FAIL | UNVERIFIED` only against actual current evidence under the existing [quality benchmark](../../mcp/docs/QUALITY_BENCHMARK.md); a pleasing preview, heuristic score or research screenshot is not native/user approval.

**Source-specific guidance:** The [Blockbench Minecraft Style Guide](https://blockbench.net/wiki/guides/minecraft-style-guide/) explains face-value hierarchy, early large color regions, pixel-cluster editing and banding avoidance. Its **Vanilla-specific look is optional**: original user-approved marketplace/stylized directions may differ in palette, texture resolution, shading grammar and geometric density. The [Blockbench editor](https://blockbench.net/) supports cubic geometry, palette painting, UV and animation; the [Microsoft Bedrock guide](https://learn.microsoft.com/en-us/minecraft/creator/documents/blockbench?view=minecraft-bedrock-stable) explains bone/UV constraints. Technique must be adapted to the approved Bedrock asset, not presumed universally compatible.

**Handoff:** pass only the approved or explicitly provisional decisions that change the current stage through the existing Reference Package/Control projection: Geometry gets form and contact, Texture gets material/value/pixel rhythm, Animation gets pivot/motion personality. Do not invent a `style_lock_id`, add a new check per-Cube, promote unverified images to construction proof, or reopen completed design choices without conflicting evidence.

## Operational Visual Craft Matrix — selectively adopted guidance (2026-11-01)

Discovery has ended by user decision. This single existing Art Direction owner distills the 56 GK/TK/AK research notes and 15 CX dossiers in [Geometry](../03-authoring/modelling/research-sources.md), [Texture](../03-authoring/texture/research-sources.md), and [Animation](../03-authoring/animation/research-sources.md). They are provenance, NOT 56 executable presets, learned weights or a licensed data set. Current approved asset/reference and Bedrock constraints always win.

| Decision / approved-current-reference trigger | Geometry-owned decision | Texture-owned decision | Animation-owned decision | Reject or defer |
| --- | --- | --- | --- | --- |
| VC-FORM — focal silhouette, accessory or opening is actually shown | Correct primary masses, volume and true gaps first (G-P02/03/06) | Preserve quieter subordinate regions; paint cannot fix form | Keep identity legible throughout required poses | One cinematic camera; depth/back unseen |
| VC-MATERIAL — supported bone, metal, wood, cloth, crystal or skin identity | Geometry only where material changes necessary depth/attachment | Intentional clusters, material-specific hue/value, limited focal accents and visual rest (TEX-P01) | Cover only source-visible exposed moving faces | Generic noise, arbitrary RGB or fixed shade quota |
| VC-STYLE — approved fantasy/cartoon/mechanical/furniture, pixel or painterly language | Subject-specific complexity, not boss-detail everywhere | Keep intended edge/cluster rhythm, not universal Vanilla/Hytale constraints | Weight, personality and range from source | Entire marketplace's style substituted for user reference |
| VC-VARIANT — cosmetic recolor versus genuine change of age/role/equipment | Reuse source-supported shape for cosmetic variant, change form for proven anatomy (G-P07) | Keep unique UV/identity and relative material contrast (UV-P01) | Reuse compatible moves, add only role-specific actions | Same label or UUID assumed to prove same motion |
| VC-MOTION — supported hinge, wing, hand, gear, stance | Choose proper parent/pivot and volume/plane/anchor (G-P05/08) | Paint actually exposed mapped surfaces and alternate form appearances | Source-backed anticipation/contact/recovery, delayed followers and motion modes | Unseen pivot, generic fixed offset or Java features presumed Bedrock |
| VC-EXPRESSION — alternate mouth/hand/eye shape | Alternative visual carrier only where needed and supported | Appearance may differ, preserve intended identity | Choose state/gesture without cloning entire clip inventory | Static paint/rotation is enough or native support unknown |
| VC-EMISSION — explicit self-luminous rune, eye or energy | Glow is not shape | Preserve base-color; separate emission/render/optional PBR when supported (TEX-P03) | Use source-supported effect/state only | Bright RGB or bloom mistaken for emission |

- **Geometry:** Project only source-grounded silhouette, shape-language, exaggeration or focal hierarchy into the existing `GEOMETRY.md` when this changes a modelling choice.

- **Animation:** Project only source-grounded readable motion personality into `ANIMATION.md`, not invented numerical timing.
- **Evidence:** Use existing native/reference paired visual verification; a missing or contradictory style fact remains `UNVERIFIED`. This guidance is not an additional Runtime gate.
## Stylized Minecraft Voxel 3D — Conditional Artist Style Bible

**Optional explanation, not a second rule set:** Read this section only when an approved asset family's stylistic grammar needs clarification. It elaborates the VC decisions above without overriding the current reference.

**Purpose:** A single shared art-direction grammar for related Blockbench/Bedrock 3D assets when the approved visual direction calls for stylized voxel forms with deliberately authored pixel-art surfaces, rather than photorealistic rendering. This is cross-domain art direction, not a second Style Lock identity, preset generator, authoring stage, or tool.

**Maturity and authority:** A user's voxel-art preference supports a broad direction, but exact proportions, shape rhythm, palette, texel scale, outlines, material identities and motion timing remain **PROVISIONAL** unless supported by the current approved reference or a separately accepted family example. Reuse a real style_lock_id only when established for that asset family. Never invent one global ID, copy marketplace imagery, infer approval from a Golden fixture or override known dimensions.

| Artist question | Conditional style grammar | Reject or defer |
| --- | --- | --- |
| Geometry: silhouette | Make supported primary masses, intended-size focal landmarks and negative spaces readable. Prefer a deliberate broad-to-secondary-to-accent shape rhythm; exaggerate only when the reference supports it. | Universal proportions, arbitrary micro-Cubes, speculative hidden depth, filler geometry that obscures the main form. |
| Texture: material | Use deliberate base/shadow/highlight/accent relations, legible pixel clusters, quiet surface regions and material-specific edge treatment. Preserve face orientation, UV resolution and identity marks. | Photo noise, universal outlines, random speckles, automatic HSL shades claimed as sampled colours, blurred paint, identical patterns on different materials. |
| Animation: personality | If the asset moves, preserve reference-supported anticipation, impact/contact and settle; match the intended visual weight without breaking attachments or planted ground contact. | One global speed, fixed keyframe count, guessed mass or stance interval, contact numbers misreported as visual approval. |
| Set consistency | Review the assets side by side at comparable display sizes; preserve simplification level, pixel rhythm, material contrast and focal accent hierarchy while allowing distinct silhouettes and palettes. | Forcing identical colours, proportions or motion amplitudes on every subject. |

**Decision illustration (hypothetical, not an observed asset):** An approved voxel sofa with a tall backrest and broad quiet fabric areas should first match that silhouette; only then apply restrained fabric shading and identity-bearing seams. Extra tiny Cubes or random high-frequency upholstery texture do not compensate for a wrong backrest. Its actual height, colour and correction remain UNKNOWN until current source views are supplied.

**AI loading/handoff:** This section is conditional expertise, not mandatory context per Cube/pixel/keyframe. Use the existing REFERENCE.json and pass only approved, decision-changing shape constraints to GEOMETRY.md, material/pixel constraints to TEXTURE.md, and motion-personality constraints to ANIMATION.md. Each domain standard and specialist remains the implementation authority. No new registry, Gateway route, Recipe engine, mandatory lookup or copied Style Bible is needed.

**Visual proof:** Compare the actual approved source image and current matching native model views at compatible camera, display scale and shading, plus mapped atlas or real playback as needed. Preserve source/asset revision identities, one named discrepancy, before/after correction and positive/rejected/ambiguous outcomes. Missing views, native execution or human art review remain **UNVERIFIED**. Style semantics and a matching hash cannot award visual PASS. The [Blockbench Minecraft Style Guide](https://blockbench.net/wiki/guides/minecraft-style-guide/) is conditional educational guidance, not permission to reproduce artwork or a mandatory Vanilla look.
